# Code Review: Week 1 Full-Stack Kanban App

Review date: 2026-08-04

## Overview

Full-stack Kanban application: Next.js 16 (static export) frontend served by a FastAPI backend, SQLite persistence, drag-and-drop via `@dnd-kit`, and an AI sidebar that mutates the board through OpenRouter structured outputs. Packaged as a single Docker image.

**Overall assessment:** The structure is clean and the feature set works end-to-end, but there are a few real bugs (one that crashes at runtime), meaningful security gaps, and some consistency issues between the documented schema, the code, and the scripts. No critical correctness issues were found in the core drag-and-drop or CRUD flow.

---

## Critical Bugs

### 1. Undefined `FALLBACK_FREE_MODEL` crashes `/api/ai/test` (High)
`backend/main.py:157` references `FALLBACK_FREE_MODEL`, but only `FREE_MODELS` (a list) is defined. If the primary model returns a `402`/insufficient-credits response, this raises `NameError: name 'FALLBACK_FREE_MODEL' is not defined` instead of falling back.

```python
if response.status_code == 402 or "Insufficient credits" in response.text:
    payload["model"] = FALLBACK_FREE_MODEL  # NameError
```

**Fix:** Use `FREE_MODELS[0]` or the same candidate-model loop already used in `/api/ai/chat`.

## Security Issues

### 2. Secrets committed to the repository (Critical)
`.env` is gitignored only inside the Docker build context (`.dockerignore`), but the file lives in the repo root and a real `OPENROUTER_API_KEY` is present in `.env`. It should never be committed. Add `.env` to a root `.gitignore` (the repo has none at root) and rotate the leaked key.

### 3. Plaintext password and hardcoded credentials (High)
- `backend/main.py:65` seeds `('user-1', 'user', 'password')` and the login check at `main.py:95` compares against the literal `"password"`. Passwords must be hashed (e.g. `bcrypt`/`argon2`).
- The same credentials are duplicated in the frontend (`LoginForm.tsx:36`), which is dead code — if it ever ran it would bypass the API entirely.

### 4. Authentication is cosmetic — no real session enforcement (High)
- `GET /api/board` explicitly allows unauthenticated access (`main.py:115-117`): the auth check is a `pass`, then the board is returned anyway.
- `PUT /api/board`, `POST /api/ai/chat`, and `/api/ai/test` never check the session cookie at all.
- The frontend treats `localStorage.kanban_authenticated` as ground truth, which any user can set. The whole auth layer is a UI gate, not a security boundary — fine for an MVP, but it should be stated as such and hardened before multi-user use.

### 5. No rate limiting or input validation on AI endpoint (Medium)
`/api/ai/chat` accepts arbitrary `history`/`message` payloads and issues outbound HTTP calls with a hardcoded 45s timeout per model. A user could spam the endpoint and burn OpenRouter credits / block the event loop. Consider an async queue, per-user rate limiting, and a cap on `history` size (it is already sliced to last 6, good).

## Data & Persistence

### 6. Schema doc vs. code divergence (Medium)
`docs/DATABASE.md` defines a normalized `columns`/`cards` JSON shape with `order` fields and a `boards.title` column. The implementation stores the **entire board (columns + cards) as one opaque JSON blob** in `boards.data` and the seed data (`DEFAULT_COLUMNS`) uses different ids (`backlog`/`card-1`) than the frontend's `INITIAL_COLUMNS` (`col-backlog`/`card-1`). Either normalize the schema or update the doc to reflect the document-store design.

### 7. New SQLite connections per request (Low)
Every handler does `sqlite3.connect(DB_PATH)` / `close()`. Fine at this scale; if the app grows, move to a single shared connection (with `check_same_thread=False`) or a pool.

### 8. Docker persistence (fixed)
Previously `kanban.db` lived only inside the container and was wiped on every `start.sh`. Now the DB path is configurable via `KANBAN_DB_PATH` and `start.sh` mounts a named volume `kanban-data:/data` (see `scripts/start.sh:12-19`). **Note:** `scripts/start.bat` and `scripts/stop.bat` were NOT updated to use the volume, so Windows users lose data on restart — keep the batch scripts in sync.

## Frontend

### 9. Hardcoded credentials in `LoginForm.tsx:36` (Medium)
The catch block grants login if the typed username/password match `"user"/"password"` even when the API call fails. This defeats the purpose of the login endpoint and hides real API failures (a broken backend silently "logs in"). Remove the fallback and surface the error instead.

### 10. `metadata` still has create-next-app defaults (Low)
`frontend/src/app/layout.tsx:15-18` — title `"Create Next App"` / description `"Generated by create next app"` should be updated.

### 11. Static export routing considerations (Low)
With `output: "export"`, everything is client-rendered and `fetch("/api/...")` calls are relative to wherever the page is served (must be behind FastAPI). This works as packaged, but any future server-side routes (e.g. `/api`) would not be exported. Acceptable for this architecture; worth a comment in `next.config.ts`.

---

## Tests

### 12. Unit tests don't exercise the backend (Medium)
`frontend/src/test/kanban.test.ts` only tests pure frontend state mutation against `INITIAL_COLUMNS`. There are **no backend tests** (no pytest) despite `docs/PLAN.md` Part 6/9 claiming pytest suites verify CRUD persistence, schema integrity, and AI structured output validity. Either add backend tests or update the plan checklist to reflect reality.

### 13. E2E tests depend on demo seed state (Low)
`e2e/kanban.spec.ts` asserts on the default board content (`"User Authentication"`, 5 columns). Because data now persists in the volume, a second run can fail (e.g. deleting `"User Authentication"` the first run makes the third test fail the second run). Seed a known DB state before the suite or run against a fresh volume.

### 14. Playwright `webServer` runs `npm run dev` (Low)
`playwright.config.ts:21` starts the Next dev server on :3000, but the production architecture serves static export via FastAPI on :8000. E2E therefore tests a different serving path than production. Consider testing against the built/exported app served by the backend.

## Code Quality & Maintainability

- **Duplicated seed data:** `DEFAULT_COLUMNS` (backend) and `INITIAL_COLUMNS` (frontend) describe near-identical boards with different ids. Keep a single source of truth.
- **`type="button"` is missing** on the drag-handle in `KanbanCard.tsx:47-53` (it's not in a form, so benign today, but it would submit forms if nested) — add `type="button"` for safety.
- **Unused imports:** `KanbanColumn.tsx` imports `Plus, Edit2, Check, X` (all used) — fine. `page.tsx` imports `arrayMove` from `@dnd-kit/sortable` (used). No obvious dead imports spotted; run `npm run lint` to confirm.
- **`cookies.txt` at repo root** looks like an accidental artifact (the `.env` was fetched/exported into it). Confirm it isn't committed secrets and remove.
- **`set -e` + fallback `||` in scripts** masks failures (e.g. `docker run` failing still prints "running at localhost"). Consider surfacing real errors.
